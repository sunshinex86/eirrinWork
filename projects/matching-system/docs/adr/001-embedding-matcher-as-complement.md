# ADR-001: 埋め込みマッチングは既存スコアラーの補完として追加する

## Status
**Accepted** ✅（2026-06-27）

## Context
マッチング品質向上の要件として、キーワードマッチングの限界を克服するため、ベクトル埋め込みを利用した意味的マッチングの導入が必要になった。

既存システムには5軸の重み付きスコアリング（`scorer.py`）が実装されており、119のテストがこれに依存している。

選択肢として以下が考えられた:
1. **既存 scorer.py を置き換える** — 5軸を新しい方式に全面変更
2. **既存 scorer.py を維持し、新しい関数を補完として追加する** — 両方を並存させる
3. **scorer.py を内部で拡張する** — 既存関数に埋め込みパラメータを追加

## Decision
**選択肢2を採用**: 既存 `scorer.py` は一切変更せず、独立した `embedding_matcher.py` を新規作成し、APIでも別エンドポイントとして公開する。

## Rationale
- 既存119テストへの影響ゼロ（置き換えの場合、全テストの修正が必要）
- ユーザーがキーワード/埋め込み/セマンティック（Claude API）の3方式を使い分け可能
- Streamlit UI でも独立したタブ（タブ3）として追加できるため、既存UIを変更不要
- 段階的導入（Phase 1 → Phase 2）が容易
- 埋め込みモデルが未インストールの場合でもフォールバック動作可能

## Consequences
**Positive**:
- 既存システムへのリグレッションリスクがゼロ
- 新しいマッチング方式の評価・比較が容易（同一データに対して2つのスコアを取得可能）
- 段階的な機能追加が可能

**Negative**:
- マッチング結果の統合表示がやや複雑になる（UIで2つのスコアを別々に表示）
- API エンドポイントが増加する（既存＋新規で6エンドポイント）
- データモデルが拡張される（`EmbeddingBreakdown` の追加）

## Alternatives Considered
### 選択肢1: 置き換え
- Pros: シンプルなアーキテクチャ
- Cons: 既存テストの全面的な書き換えが必要、ロールバックが困難

### 選択肢3: 内部拡張
- Pros: APIインターフェースが変わらない
- Cons: `scorer.py` の複雑度が増大、既存テストの互換性維持が困難、密結合
